**A read of a project's repository cannot overwrite it.** `krewe project repository` took an optional
address and then a repository. With one argument it read that argument as the repository and wrote
it. So an operator who typed the address of a project to see what it works in recorded that address
as the repository of whichever project they were standing in, and the answer was the sentence a read
prints. The overwrite came back as a confirmation that the setting was correct.

One argument is still the write, because every message in the tool teaches that form first. Where the
argument also names a project the system holds, the command has two readings and now takes neither.
It refuses, names the project in scope as well as the argument, and prints the spelling of each
reading.

```
krewe project repository show acme/house-bills          read that project, record nothing
krewe project repository acme/other acme/house-bills    record it as the repository of acme/other
```

`show` is the read the intent had nowhere to go before. Two arguments always recorded, and the tool
takes no flags, so the only spelling within reach was the one that destroys data.

A write says it wrote. It says what it recorded and what the project worked in before, which a read
has nothing to say about, so the two lines can no longer be mistaken for each other.

A write that says no kind now keeps the kind the project holds. It used to clear it, so an operator
correcting an address dropped that project from private to public in the same command and was told
its pipeline minutes were free. A project nobody has told is still public.
